# تصميم Dashboard الرئيسية لتطبيق التوصية الغذائية

## الغرض من الشاشة

لوحة التحكم هي نقطة العودة اليومية بعد تسجيل الدخول. لا تحاول تمثيل استهلاك أو تقدم لم يسجله المستخدم؛ بل تعرض **الأهداف المحسوبة فعليًا**، وتمنح المستخدم أقصر طريق إلى الوجبة أو الخطة التالية، وتوضح كيف يتعلم النظام من تفاعله.

> المبدأ التصميمي: تظهر المعلومة التي تساعد المستخدم على اتخاذ الخطوة التالية أولًا، ثم المعلومات التفسيرية، ثم الاختصارات الثانوية.

## التسلسل البصري على شاشة هاتف عربية

| الترتيب | المكوّن | الارتفاع التقريبي | البيانات | الإجراء الأساسي |
|---:|---|---:|---|---|
| 1 | رأس الترحيب | 64 px | الاسم الأول والتاريخ | فتح الملف الشخصي. |
| 2 | بطاقة الهدف اليومي | 160 px | السعرات والمغذيات المستهدفة المحسوبة من API | الانتقال إلى التوصيات. |
| 3 | بطاقة «خطوتك التالية» | 136 px | الوجبة المقترحة بحسب وقت اليوم | فتح شاشة التوصيات مع نوع الوجبة محددًا. |
| 4 | بطاقة حالة التخصيص | 92–116 px | حالة Cold Start أو جاهزية CF | فتح التوصيات للتفاعل مع العناصر. |

## قواعد السلوك والحالات

| الحالة | ما يظهر للمستخدم | ما لا ينبغي إظهاره |
|---|---|---|
| تحميل الأهداف | Skeleton أو مؤشر تحميل داخل بطاقة الهدف | شاشة فارغة أو Spinner يغطي الصفحة كاملة. |
| تعذر الاتصال | بطاقة خطأ مع زر «إعادة المحاولة» | رسالة تقنية مثل `DioException`. |
| Cold Start | «يتعلم من إعجابك وحفظك وعدم اهتمامك» مع عدد تفاعلات المستخدم | الادعاء بأن CF يعمل قبل اكتمال الحد الأدنى للبيانات. |
| CF جاهز | «التخصيص من تفضيلاتك وتفاعلات مشابهة أصبح متاحًا» | كشف أرقام أو مستخدمين آخرين. |
| عدم وجود سجل استهلاك | لا يظهر تقدم أو سعرات مستهلكة غير حقيقية | دائرة تقدم صفرية توحي بفشل المستخدم. |
| حساسية مسجلة | تبقى في الملف الشخصي؛ لا تظهر كل مرة على Dashboard | ادعاء أن الواجهة تمثل ضمانًا طبيًا. |

## الهوية البصرية والتفاعل

تستخدم الشاشة ألوان المشروع الحالية: الأزرق `primary` للهدف والإجراء الأساسي، والأخضر `secondary` للخطة والتقدم المفهوم، والبرتقالي `accent` للبحث والتنبيه الخفيف، والأحمر `danger` للأخطاء والحساسية عند الحاجة فقط. يظل لون الخلفية محايدًا، وتكون البطاقات ذات زوايا 20px ومسافات رأسية 16px. لا يعتمد أي معنى على اللون وحده؛ تدعمه دائمًا أيقونة ونص عربي واضح.

يكون زر الإجراء الأساسي بعرض البطاقة، مثل «استكشف اقتراحات الغداء»، لأن هذا هو المسار الأكثر أهمية. أما بطاقات الإجراءات السريعة فهي أزرار لمسية لا يقل ارتفاعها عن 48px، ولها عنوان وأيقونة. الضغط على بطاقة «التخصيص» يفتح شاشة التوصيات، حيث توجد أزرار التفاعل الصريح التي تفيد المحرك فعليًا.

## عناصر قابلة للتوسع لاحقًا

عند تنفيذ شاشة سجل وجبات وربطها ببيانات فعلية، يمكن إضافة قسم «ملخص ما سجلته اليوم» بين بطاقة الهدف وبطاقة الخطوة التالية. لا يُضاف هذا القسم قبل توفر سجل موثوق للمستهلكات؛ فتمييز **الهدف المخطط** عن **المستهلك الفعلي** ضروري لسلامة تجربة المستخدم وصدق العرض الأكاديمي.

يمكن لاحقًا إضافة قسم «المحفوظة» فقط بعد إنشاء مسار API لاسترجاع العناصر ذات تفاعل `save`. حتى ذلك الوقت، يوجّه زر «التخصيص» إلى التوصيات بدل وضع بطاقة محفوظات وهمية.

## معايير القبول

تعد الشاشة مكتملة عندما يستطيع المستخدم خلال ثوانٍ: معرفة هدفه اليومي، فتح توصية مرتبطة بالوجبة المناسبة، فهم ما إذا كان التخصيص التعاوني متاحًا، فتح الخطة الأسبوعية، وتعديل ملفه. يجب أن تعمل الصفحة في حالات التحميل والخطأ والبيانات الصحيحة، وأن تحافظ على اتجاه RTL في جميع الأزرار والصفوف.


## ربط تتبع اليوم بسجل الوجبات الفعلي

أصبحت بطاقة «متابعة اليوم» متصلة بالمسار `GET /users/meal-logs/daily-progress`. يختار الخادم اليوم المطلوب، ويجمع فقط سجلات `MealLog` التي تخص المستخدم الحالي ضمن الفترة من بداية اليوم إلى بدايته في اليوم التالي. ثم يقارن الاستهلاك المسجل بالأهداف المحسوبة من الملف الشخصي الحالي. لا تُخلط الأهداف بالاستهلاك، ولا يُنشأ تقدم وهمي عند غياب السجلات.

| الحقل | المصدر | الاستخدام في البطاقة |
|---|---|---|
| `target` | حساب الاحتياجات الحالي في الخادم | المقام في عبارة السعرات والمغذيات. |
| `consumed` | مجموع سجلات `MealLog` في اليوم المحدد | البسط في العبارة وشريط التقدم. |
| `remaining` | `target - consumed` | يوضح المتبقي أو مقدار التجاوز. |
| `progress_ratio` | `consumed / target` | يملأ شريط التقدم؛ يقيد العميل عرضه بين 0 و1 فقط. |
| `logged_meals` | عدد سجلات الوجبات لذلك اليوم | يوضح ما إذا كان هناك استهلاك فعلي مسجل. |

عند اختيار المستخدم توصية وتأكيد زر **«سجّل كوجبة مأكولة»**، يرسل التطبيق تفاصيل الحصة والمغذيات المعروضة إلى `POST /users/meal-logs`، ثم يبطل مزود `dailyNutritionProgressProvider` لتحميل الأرقام الجديدة في Dashboard. يظل هذا الإجراء منفصلًا عن أزرار الإعجاب والحفظ وعدم الاهتمام؛ فتسجيل الوجبة لا يعد تفضيلًا ضمنيًا لتدريب التوصية التعاونية.

> دقة التتبع مساوية لدقة السجلات التي يضيفها المستخدم. إذا عدّل المستخدم الحصة أو اختار طعامًا من دون تسجيله، فلن تمثل البطاقة ذلك تلقائيًا. لهذا تعرض الواجهة بوضوح عبارة «لا توجد وجبات مسجلة» عندما تكون القيمة صفرًا.

## الاختبارات المرتبطة

يشمل التحقق اختبار API يجمع سجلات اليوم فقط ويستبعد اليوم السابق وسجلات مستخدم آخر، واختبارًا لحالة اليوم الفارغ، واختبارات وحدة لنموذج `DailyNutritionProgress`، واختبارات Widget للتحقق من ظهور قيم الاستهلاك والمتبقي وحالة السجل الفارغ في Dashboard.

لتشغيل اختبارات Flutter في بيئة تطوير تحتوي Flutter SDK:

```bash
cd app
flutter analyze
flutter test
```


## أخطاء Dashboard الشائعة وكيف يتجنبها التطبيق

الـDashboard ليست تقريرًا ثابتًا؛ هي نقطة قرار سريعة. لذلك يكون الخطأ التصميمي ضارًا عندما يغيّر فهم المستخدم لبياناته أو يجعل الإجراء الصحيح غير واضح. يوضح الجدول التالي المخاطر العملية الخاصة بتطبيق التوصية الغذائية وطريقة معالجتها.

| الخطأ الشائع | أثره على المستخدم أو النظام | وضع التطبيق الحالي أو الإجراء المطلوب |
|---|---|---|
| عرض هدف السعرات على أنه استهلاك فعلي | يشعر المستخدم بتقدم غير حقيقي أو يظن أن بياناته سجلت. | عولج: تعرض البطاقة `consumed / target` وعدد الوجبات المسجلة، وتظهر حالة فارغة صريحة عند عدم وجود سجل. |
| مزج «أكلت الوجبة» مع «أعجبتني الوجبة» | يلوث بيانات CF ويجعل التوصية تستنتج تفضيلات غير معلنة. | عولج: زر تسجيل الوجبة منفصل عن أزرار التفاعل الصريح. |
| إخفاء حالة التحميل أو الخطأ | يفسر المستخدم البطاقة الفارغة على أنها صفر استهلاك أو هدف غير موجود. | عولج: توجد حالة تحميل وإعادة محاولة مستقلة للأهداف وللتقدم اليومي. |
| التعامل مع النسبة فوق 100% كخطأ أو إخفاء التجاوز | يفقد المستخدم معلومة الفرق بين المتبقي والتجاوز. | عولج: يقيد شريط التقدم بصريًا، بينما يظهر النص مقدار التجاوز الحقيقي. |
| كثافة عالية من الأرقام دون أولوية | يزيد الحمل المعرفي ويجعل المستخدم يترك الشاشة من دون إجراء. | عولج جزئيًا: تعرض البطاقة السعرات أولًا ثم وحدات الماكرو المختصرة، وتبقى التفاصيل في شاشات متخصصة. |
| أزرار لا تشرح أثرها | قد يسجل المستخدم وجبة أو تفضيلًا من دون قصد. | عولج: زر «سجّل كوجبة مأكولة» يطلب تأكيدًا، وأزرار التفاعل تملك tooltips ورسائل نجاح أو فشل. |
| عدم اتساق بيانات اليوم بعد حفظ وجبة | يضعف الثقة إذا بقيت Dashboard بالقيم القديمة. | عولج: يبطل التطبيق `dailyNutritionProgressProvider` بعد الحفظ ويعيد تحميله. |
| تجاهل حالات المستخدم الجديد | تظهر رسالة تقنية أو توصيات تعاونية غير ناضجة. | عولج: تعرض Dashboard حالة Cold Start وتوجه المستخدم للتفاعل الاختياري، بينما يبقى CBF هو المسار الافتراضي. |
| استخدام لون فقط للدلالة على حالة خطرة أو نجاح | يضعف قابلية الوصول للمستخدمين ذوي صعوبات تمييز اللون. | مطلوب في كل تطوير قادم: نص وصفي وأيقونة مع اللون، واختبار تباين على جهاز فعلي. |
| افتراض أن المستخدم سيعرف مصدر الأرقام | يضعف قابلية التفسير في مشروع التخرج. | عولج: يوثق المصدر في النصوص، وتبقى الأهداف والسجل والتفضيل مسارات بيانات منفصلة. |

### قائمة تحقق قبل دمج أي تعديل للواجهة

قبل دمج أي بطاقة جديدة، يجب التحقق من خمس نقاط: أن كل رقم يحمل مصدرًا معروفًا، وأن حالتي التحميل والخطأ موجودتان، وأن الإجراء الرئيسي يغير الحالة بصورة متوقعة، وأن النصوص العربية واتجاه RTL واضحان، وأن البطاقة لا تقدم ادعاءً صحيًا أو طبيًا. كما ينبغي تشغيل اختبارات Widget للحالة الطبيعية والفارغة والخاطئة، ثم مراجعة الشاشة على هاتف حقيقي لا على المحاكي فقط.
