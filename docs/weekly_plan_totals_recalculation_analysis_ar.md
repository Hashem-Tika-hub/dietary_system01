# تحليل تطوير تعديل الخطة الأسبوعية وإعادة حساب المجاميع

## الهدف الوظيفي

عند اختيار المستخدم بديلًا لعنصر داخل الخطة الأسبوعية، يجب ألا يقتصر النظام على استبدال اسم الطعام فقط. يتعين عليه إعادة حساب **سعرات الوجبة، البروتين، الكربوهيدرات، الدهون، مجموع اليوم، والفرق عن الهدف المخطط**، ثم إعادة النتيجة إلى التطبيق مباشرة. بهذه الطريقة تصبح خطة الأسبوع خطة قابلة للمراجعة وليست قائمة عناصر منفصلة.

> الخطة الأسبوعية هي **تخطيط مسبق**. لذلك تستخدم أهداف المستخدم اليومية الأصلية، ولا تستخدم سجل الوجبات أو المتبقي اليومي لتعديل مجاميع الأسبوع. سجل الوجبات مخصص لمتابعة الاستهلاك الفعلي في Dashboard، ولا يمثل تفضيلًا ولا يدخل في CF.

---

## الوضع الحالي والفجوة

المسار الحالي لاستبدال عنصر في الخطة يثبت أن البديل يخص المستخدم والخطة والخانة، ويحسب له حصة واقعية وفق خانة الوجبة. لكنه يحفظ `plan_data` بعد الاستبدال من دون عقد موحد لمجاميع الوجبات أو اليوم. لذلك لا يستطيع التطبيق بيان أثر الاستبدال، مثل: «زاد بروتين الغداء 8g» أو «أصبح مجموع اليوم أقل من هدفه بـ 120 kcal».

| العنصر | السلوك الحالي | السلوك المقترح |
|---|---|---|
| استبدال الطعام | تحديث عنصر الخانة المختارة. | تحديث العنصر ثم إعادة حساب المجاميع المتأثرة. |
| مجاميع الوجبة | تُستنتج ضمنيًا من العناصر إن احتاجتها الواجهة. | عقد صريح: السعرات والماكرو والهدف والفرق وحالة الخانات. |
| مجاميع اليوم | غير متاحة كبيانات منظمة. | ملخص يومي من جميع الوجبات المخططة. |
| أثر الاستبدال | لا يعود للمستخدم. | فرق قبل/بعد للوجبة واليوم. |
| الأمان | البديل يمر عبر توصيات المحرك. | يبقى الفلتر الصارم للحساسية والقيود قبل البحث والترتيب. |

## تصميم البيانات المقترح

لا حاجة إلى جدول جديد في المرحلة الأولى. تبقى العناصر المصدر الأساسي داخل `WeeklyPlan.plan_data`، وتُحسب المجاميع بشكل حتمي من العناصر عند إنشاء الخطة أو استبدال عنصر. يمنع ذلك تخزين قيم مشتقة قد تصبح قديمة أو غير متزامنة.

```text
WeeklyPlanResponse
├── id
├── plan
│   └── <day>
│       └── <meal>: [food items]
├── totals
│   └── <day>
│       ├── planned_calories
│       ├── calories
│       ├── protein_g
│       ├── carbs_g
│       ├── fat_g
│       ├── calorie_delta
│       ├── completion_ratio
│       ├── missing_required_slots
│       └── meals
│           └── <meal>: { target_calories, calories, protein_g, carbs_g, fat_g, calorie_delta }
└── created_at
```

تحتسب المجاميع من العناصر التي لا تحمل `missing: true` فقط. تبقى الخانات الإلزامية المفقودة مرئية في `missing_required_slots` ولا تُخفى بصفر يوحي بأن الوجبة مكتملة.

| الحقل | طريقة الحساب | الاستخدام في الواجهة |
|---|---|---|
| `calories` | مجموع سعرات العناصر الفعلية بعد حجم الحصة. | إجمالي الوجبة/اليوم. |
| `protein_g`, `carbs_g`, `fat_g` | مجموع ماكرو العناصر بعد حجم الحصة. | مقارنة شفافة بالهدف. |
| `target_calories` | هدف الوجبة من `UserProfile.get_meal_targets()`. | مرجع تخطيطي، لا استهلاك فعلي. |
| `calorie_delta` | `calories - target_calories`. | يوضح الزيادة أو النقص. |
| `completion_ratio` | `calories / planned_daily_calories` عند وجود هدف موجب. | مؤشر اكتمال الخطة، وليس تقييمًا صحيًا. |
| `missing_required_slots` | عدد الخانات الإلزامية غير المتاحة بعد القيود. | تحذير بنيوي صادق للخطة. |

## عقد API المقترح

### قراءة الخطة

يبقى `GET /recommendations/weekly` متوافقًا مع التطبيق الحالي، مع إضافة حقل اختياري `totals`. لا تتغير قائمة العناصر في `plan`.

```json
{
  "id": 12,
  "plan": { "الأحد": { "lunch": [] } },
  "totals": {
    "الأحد": {
      "planned_calories": 2100,
      "calories": 2040,
      "protein_g": 126.4,
      "carbs_g": 248.7,
      "fat_g": 67.9,
      "calorie_delta": -60,
      "completion_ratio": 0.97,
      "missing_required_slots": 0,
      "meals": {
        "lunch": {
          "target_calories": 735,
          "calories": 710,
          "protein_g": 41.2,
          "carbs_g": 82.1,
          "fat_g": 18.4,
          "calorie_delta": -25
        }
      }
    }
  }
}
```

### تنفيذ الاستبدال

يبقى طلب `POST /recommendations/weekly/swap` كما هو من حيث `plan_id`, `day`, `meal`, `slot`, و`new_fdc_id`. تتوسع الاستجابة لتشمل الخطة المحدثة وملخصًا محليًا للتغيير:

```json
{
  "id": 12,
  "plan": { "الأحد": { "lunch": [] } },
  "totals": { "الأحد": {} },
  "change_summary": {
    "day": "الأحد",
    "meal": "lunch",
    "slot": "بروتين",
    "calories_delta": 35,
    "protein_delta_g": 8.2,
    "carbs_delta_g": -1.0,
    "fat_delta_g": 2.1
  }
}
```

لا يكون `change_summary` مصدر الحقيقة؛ إنه فرق عرض محسوب من إجمالي الوجبة قبل وبعد. مصدر الحقيقة يظل عناصر الخطة والمجاميع الحتمية المشتقة منها.

## خوارزمية التنفيذ المقترحة

ينفذ الاستبدال ضمن معاملة قاعدة بيانات واحدة حتى لا تُحفظ خطة محدثة مع مجاميع قديمة.

1. يتأكد المسار من ملكية الخطة للمستخدم ومن صلاحية `day`, `meal`, و`slot`.
2. يحصل على البدائل من المحرك بعد تطبيق قيود نوع الوجبة والحساسية وعدم الرغبة والقيود الغذائية الصارمة.
3. ينشئ العنصر البديل بحجم حصة يوافق هدف **خانة** الوجبة، وليس هدف اليوم كاملًا.
4. يحتفظ بنسخة مختصرة من إجمالي الوجبة واليوم قبل الاستبدال.
5. يستبدل العنصر، ثم يعيد حساب مجاميع الوجبة واليوم مباشرة من `plan_data`.
6. يحفظ `plan_data` ويعلّم عمود JSON بأنه تغير باستخدام `flag_modified` ثم ينفذ `commit`.
7. يعيد الخطة و`totals` وفرق ما قبل/بعد للواجهة.

```text
validate ownership and slot
        ↓
find eligible alternative (hard filters first)
        ↓
compute slot-based portion
        ↓
calculate old meal/day totals
        ↓
replace item in plan_data
        ↓
recalculate totals from plan_data
        ↓
persist atomically and return plan + totals + change summary
```

## طبقة خدمة مقترحة

يفضل وضع الحساب في دوال نقية قابلة لاختبار الوحدة، مثل `api/services/weekly_plan_totals.py`:

```python
def summarize_meal(items: list[dict], target_calories: float) -> dict: ...
def summarize_day(day_plan: dict, meal_targets: dict, daily_target: float) -> dict: ...
def summarize_week(plan_data: dict, targets: dict) -> dict: ...
def diff_summaries(before: dict, after: dict) -> dict: ...
```

هذا الفصل مهم لأن المسار لا ينبغي أن يحمل منطق الجمع والتحقق، ولأن الدوال النقية تسمح باختبار العناصر المفقودة والصفرية والحصص والمجاميع بدقة من دون قاعدة بيانات أو نموذج تعلم آلي.

## قواعد الأمان وعدم خلط الإشارات

| القاعدة | التطبيق في التحسين |
|---|---|
| الحساسية والقيود الصارمة | تنفذ قبل توليد البديل، ولا يمكن لدرجة CBF أو CF تجاوزها. |
| سجلات الوجبات | لا تدخل في CF ولا تغير الجاهزية؛ لا تستخدم هنا إلا في ميزة المتبقي اليومي المنفصلة عن التخطيط الأسبوعي. |
| K-Means | يستخدم لتنويع البدائل عند الإمكان، ولا يعد قيدًا طبيًا ولا يمنع البديل الوحيد المؤهل. |
| القيم الناقصة | لا تُخترع قيم غذائية؛ العناصر ذات الخانة المفقودة تظهر كتغطية ناقصة. |
| لغة النظام | تعرض فروقًا كمية وتخطيطية، من دون تشخيص أو وصف علاجي. |

## خطة الاختبارات

تسبق الواجهة اختبارات وحدة للخدمة الجديدة، ثم اختبارات API للاستبدال.

| الاختبار | النتيجة المتوقعة |
|---|---|
| عناصر وجبة عادية | مجموع السعرات والماكرو يساوي مجموع عناصرها بعد الحصة. |
| عنصر `missing` | لا يزيد السعرات، ويزيد عداد الخانات الإلزامية الناقصة. |
| استبدال بروتين | يتغير إجمالي الغداء واليوم و`change_summary` بالقيم الصحيحة. |
| بديل محظور بالحساسية | لا يصل إلى دالة الاستبدال ولا يغير الخطة. |
| مستخدم آخر | يحصل على `404` ولا يقرأ أو يغير الخطة. |
| إعادة تحميل الخطة | تعيد نفس `totals` المحسوبة من `plan_data`. |
| حصة بصفر سعرات | لا تسبب قسمة على صفر ولا تجعل المجاميع غير رقمية. |

---

## معايير القبول للمرحلة التالية

يُعد التحسين مكتملًا عندما يعرض التطبيق إجمالي كل وجبة وكل يوم، ويظهر الفرق الكمي بعد الاستبدال، وتنجح اختبارات المجاميع والملكية والحساسية، وتبقى الخطط الأسبوعية منفصلة عن سجل الاستهلاك الفعلي وCollaborative Filtering. لا يقاس النجاح بدقة سريرية؛ بل بصحة الحساب واتساق العقد وغياب تعارضات القيود المعروفة.
