# تدقيق المستودع وخطة تنظيفه وإعادة تنظيمه

## النطاق

شمل التدقيق الملفات المتتبعة في الجذر، وطبقة FastAPI، وتطبيق Flutter، والترحيلات، والبيانات، والنماذج، والوثائق، والتقارير، وCI. الهدف ليس حذف ملفات عشوائيًا، بل فصل **كود التشغيل** عن **بيانات التدريب** و**المخرجات المؤقتة** و**أدوات المشروع التاريخية**.

## الحالة السابقة ومشكلة قاعدة البيانات

كان الملف المتتبع `data/dietary.db` قاعدة SQLite قديمة تحتوي فقط `users` و`meal_logs` و`weekly_plans`. لم تتضمن `alembic_version` أو جداول الكتالوج والعناصر الغذائية والحساسية. في المقابل، كان التطبيق يملك ترحيلات سليمة ونماذج `Food` و`FoodNutrient` و`FoodAllergen`، لكن مسار `/foods` يقرأ `data/foods_clean.csv` مباشرة عبر Pandas. أدى ذلك إلى وجود مصدرين متباعدين للحقيقة: CSV للبحث والتوصية، وقاعدة بيانات ناقصة لسجل الوجبات والحساسية.

> تم التأكد أن تشغيل Alembic على قاعدة جديدة ينشئ الجداول الـ14 المطلوبة، وأن استيراد الكتالوج يضيف 456 طعامًا و4,104 سجل عناصر غذائية و456 حصة افتراضية بدون انتهاكات مفاتيح خارجية. لا يصنع الاستيراد دليل حساسية غير موجود في المصدر؛ لذلك تبقى أدلة الحساسية ناقصة إلى أن تراجع من مصدر موثق.

## التغييرات المنفذة في هذه الدفعة

| المجال | التغيير | الأثر |
|---|---|---|
| مصدر كتالوج الطعام | أضيفت خدمة `api/services/catalog_import.py` وأمر `scripts/import_food_catalog.py`. | يتحول CSV إلى مدخل استيراد قابل لإعادة التشغيل، بدل أن يكون قاعدة بيانات وقت تشغيل. |
| استعلام API | تم تحويل `api/routes/foods.py` إلى SQLAlchemy باستخدام `Food` و`FoodNutrient`. | بحث Flutter والحساسية والكتالوج يعملون على مصدر قاعدة بيانات واحد. |
| مخطط الكتالوج | أضيفت حقول `health_score` و`diabetic_friendly` و`low_sodium` و`is_high_protein` وترحيل Alembic جديد. | تبقى استجابة بحث الطعام متوافقة مع Flutter بعد ترك CSV. |
| جاهزية القاعدة | توسع `assert_database_schema_is_current()` ليطلب جداول الكتالوج الأساسية. | لا يبدأ API على قاعدة قديمة تبدو صالحة ظاهريًا لكنها تفتقد الغذاء والحساسية. |
| التهيئة | صار `init_database.py` يطبق الترحيلات ويستورد الكتالوج ثم يفحص CRUD والمصادقة. | إنشاء قاعدة تطوير جديدة يعيد حالة واضحة ومقيسة. |
| سلامة Git | أزيل `.env` وملف SQLite القديم وملفات `__pycache__` ومخرج Gradle المتتبع. | لا تُحفظ أسرار أو مخرجات بناء أو بيانات تطوير قديمة في المستودع. |
| إعدادات آمنة | أضيف `.env.example` بقيم مثال فقط. | توجد نقطة بدء آمنة من دون كشف أسرار. |
| Flutter | دُمج تنفيذ `ApiClient` داخل `app/lib/core/api_client.dart` تحت الاسم الصحيح. | أزيل الاعتماد على اسم `api_clinet.dart` ذي الخطأ الإملائي. |

## تصنيف المجلدات والملفات

| المنطقة | التصنيف | القرار |
|---|---|---|
| `api/` | أساسي للتشغيل | يحتفظ به؛ تنظف قاعدة البيانات والكتالوج في هذه الدفعة. |
| `app/` | أساسي للواجهة | يحتفظ به؛ أزيل مخرج Android المتتبع وصحح اسم عميل API. |
| `api/migrations/` و`alembic.ini` | أساسي لمخطط البيانات | يحتفظ به كالمسار الوحيد لتطوير المخطط. |
| `data/processed/foods_clean.csv` | مدخل معالجة/تدريب | كتالوج معالج لاستيراد CSV وتدريب CBF؛ ليس مصدر API مباشرًا. |
| `models/cbf_model.pkl` | أصل تشغيل مؤقت | يبقى حتى نقل الأصول إلى `artifacts/models/` وتحديث مسارات التحميل. |
| `data/raw/external/` و`data/raw/local_food_source.csv` | بيانات خام | نُقلت إلى طبقة `raw/` وتبقى قابلة لإعادة المعالجة. |
| `data/outputs/analysis/charts/` و`data/outputs/` | مخرجات تحليل وتجارب | نُظمت كـ `outputs/` ولا تُستخدم كمدخلات للتطبيق. |
| السكربتات `01` إلى `10` و`run_phase*` و`translate_prints.py` | أدوات تاريخية/تدريب | لا تُحذف الآن لأن بعض وحدات التشغيل ما زالت تستورد `05` و`07` و`09` ديناميكيًا؛ تنقل إلى `ml/` و`tools/legacy_pipeline/` في دفعة مستقلة. |
| `08_cf_model.py` والبيانات الاصطناعية ونماذج CF القديمة | مرشح للأرشفة | سياسة CF الحالية لا تستخدمها لتفعيل التوصية؛ لا تنقل قبل إزالة الاستيراد الديناميكي وتوسيع الاختبارات. |
| `requirements.txt` و`requirements-dev.txt` | تبعيات موحدة | `requirements.txt` مصدر تشغيل واحد للتطوير وRailway، و`requirements-dev.txt` يضيف أدوات الاختبار فقط. |

## الهيكل المستهدف

```text
api/                 # API، مسارات، خدمات، ترحيلات، اختبارات
app/                 # Flutter
ml/core/             # CBF، hybrid، ملف المستخدم وقواعد الوجبات
ml/training/         # تدريب وتقييم غير تشغيليين
tools/catalog/       # استيراد وتدقيق الكتالوج
tools/legacy_pipeline/ # أدوات جمع/تنظيف تاريخية
data/raw/            # مصادر CSV الأصلية
data/processed/      # مدخلات التدريب المعالجة
artifacts/models/    # نماذج قابلة لإعادة الإنشاء
docs/architecture/   # قرارات البنية
```

## قرارات السلامة والجودة

لا يجوز أن تفسر غياب بيانات الحساسية كدليل أمان. عند حساسية معلنة، تصنّف البيانات الخالية من `FoodAllergen` أو `IngredientAllergen` كبيانات غير مكتملة ولا يسمح محرك الأهلية بإعادتها عبر الترتيب. كذلك يبقى `MealLog` للحساب اليومي فقط، ولا يصبح تفضيلًا أو مدخلًا لتفعيل Collaborative Filtering.

## الدفعة التالية الموصى بها

نُقلت وحدات ML التشغيلية إلى `ml/core` وفُصلت البيانات إلى `data/raw` و`data/processed` و`data/fixtures` و`data/outputs` مع تحديث مساراتها. الدفعة التالية الموصى بها هي نقل أدوات التدريب والتقييم التاريخية إلى `tools/legacy_pipeline` ثم نقل أصول النماذج القابلة لإعادة الإنشاء إلى `artifacts/models` بعد إزالة الاعتمادات الديناميكية وتوسيع الاختبارات.
