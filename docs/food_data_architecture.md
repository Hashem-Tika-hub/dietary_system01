# بنية بيانات الأطعمة والوجبات والتوصيات

## نطاق المرحلة

هذه المرحلة تطور **طبقة البيانات** فقط. لم تُستبدل FastAPI أو Flutter أو خوارزميات Content-Based Filtering وK-Means وCollaborative Filtering، ولم تُضف بيانات غذائية أو تفاعلات مستخدمين مصطنعة. النظام يظل نظام دعم قرار غذائي، وليس أداة تشخيص أو علاج طبي.

## 1. البنية القديمة

كان كتالوج الطعام يعتمد على جدول `foods` مع حقول نصية مثل `category` و`meal_tags`، وعلى جداول `food_nutrients` و`food_portions` و`food_allergens`. أما الوجبات المركبة فكانت تمثل غالبًا داخل JSON الخاص بـ`weekly_plans` أو داخل منطق التوصية، من دون جدول علائقي مستقل لمكونات الوجبة. كما كانت `User` تحتوي حقول JSON للتفضيلات القديمة (`allergies` و`dislikes` و`favorites`) لأسباب توافق خلفي.

هذه البنية كانت صالحة للـAPI الحالي، لكنها لا تفصل بوضوح بين **Food** كصنف مفرد و**Meal** كتركيب من عدة أطعمة، ولا توفر سجلًا عامًا للتوصيات الخام والتفاعلات المستقبلية.

## 2. البنية الجديدة

أضيفت طبقة تطبيع additive عبر migration `e7f1a2b3c4d5`، مع الحفاظ على الحقول القديمة وعدم حذف بيانات قائمة.

| الكيان | الغرض |
|---|---|
| `foods` | الصنف الغذائي المفرد؛ يحتفظ بـ`category` و`meal_tags` للتوافق، ويضيف `category_id`. |
| `food_categories` | قاموس تصنيفات مضبوط مثل `protein` و`vegetables` و`grains`. |
| `meal_types` | قاموس مستقل لأنواع الوجبات: `breakfast`, `lunch`, `dinner`, `snack`. |
| `food_meal_types` | علاقة many-to-many بين الطعام وأنواع الوجبات. |
| `dietary_tags` | قاموس وسوم مثل `high_protein` و`low_sodium` و`diabetes_friendly`. |
| `food_dietary_tags` | علاقة many-to-many بين الطعام والوسوم مع مصدر وجودة البيانات. |
| `meals` | وجبة مركبة قابلة لإعادة الاستخدام، من دون تخزين مغذيات مكررة. |
| `meal_ingredients` | مكونات الوجبة، كل منها يشير إلى `foods` مع `quantity`, `unit`, و`position`. |
| `meal_meal_types` | علاقة many-to-many بين الوجبة ونوع الوجبة. |
| `user_food_preferences` | تفضيل صريح مضبوط: `favorite`, `dislike`, أو `exclude`. |
| `user_dietary_preferences` | ربط المستخدم بوسم غذائي مضبوط. |
| `recommendations` | تاريخ ما عُرض للمستخدم، ومصدره ودرجته. |
| `user_interactions` | أحداث خام مثل `VIEW`, `ACCEPT`, `REJECT`, `SWAP`, `FAVORITE`, `CONSUMED`, و`RATE`. |

## 3. العلاقات والقيود

```text
Food ──< FoodNutrient
Food ──< FoodPortion
Food ──< FoodMealType >── MealType
Food ──< FoodDietaryTag >── DietaryTag
Meal ──< MealIngredient >── Food
Meal ──< MealMealType >── MealType
User ──< UserFoodPreference >── Food
User ──< UserDietaryPreference >── DietaryTag
User ──< Recommendation ──> Food أو Meal
User ──< UserInteraction ──> Food أو Meal أو Recommendation
```

تمنع القيود الأساسية القيم غير الصالحة: الكميات يجب أن تكون موجبة، ووحدات مكونات الوجبة محصورة في `g`, `ml`, `piece`, و`serving`، والتقييم من 1 إلى 5، وقيم التفضيل ومصدر التوصية وأنواع التفاعل مضبوطة. يجب أن يشير كل سجل توصية أو تفاعل إلى طعام أو وجبة. تمنع القيود والمفاتيح الخارجية السجلات اليتيمة.

## 4. التطبيع الغذائي

المصدر `data/processed/foods_clean.csv` يحتوي 456 سجلًا و24 عمودًا. المغذيات الأساسية والإضافية تفسر على أساس **100 غرام**، وتخزن طبقة قاعدة البيانات `basis_grams=100` والوحدة في `food_nutrients`. تشمل الحقول المستوردة السعرات والبروتين والكربوهيدرات والدهون والألياف والسكر والصوديوم والكالسيوم والحديد.

لم يضف التنفيذ قيمًا مفقودة أو يخمن حجم الحصة. الحصة الافتراضية الحالية `100 g` موثقة في `food_portions`، بينما لا توجد في CSV أعمدة صريحة لحجم ووحدة حصة واقعية. لذلك تحتاج حصص العرض التفصيلية إلى مراجعة مصدرية لاحقة.

تُحسب مغذيات الوجبة مستقبلًا من `meal_ingredients` ومن مغذيات الطعام لكل 100 غرام مع تحويل الوحدة عند توفر معامل تحويل موثوق. لا تُخزن مغذيات الوجبة يدويًا في هذه المرحلة.

## 5. التصنيفات والوسوم

تظل قيمة `foods.category` القديمة محفوظة، ويُنشأ مقابلها `food_categories.code` مضبوط. كما يحول `meal_tags` القديمة إلى صفوف في `food_meal_types`. تُحوّل أعلام الكتالوج الموثقة نسبيًا إلى وسوم `high_protein`, `low_sodium`, و`diabetes_friendly` مع `data_quality=estimated`؛ لا تُنشأ وسوم `vegan` أو `gluten_free` دون دليل مصدر.

## 6. الحساسية والسلامة

تبقى `food_allergens` و`ingredient_allergens` مصدر أدلة الحساسية المنفصل. لا تعتبر العلاقة المفقودة دليلًا على غياب المسبب. يجب تنفيذ فلاتر الحساسية والاستبعادات الصلبة قبل أي ترتيب CBF أو تنويع K-Means. كما أن الاستبعاد النصي لمؤشرات الخنزير أو الكحول ليس شهادة حلال رسمية.

## 7. التفضيلات والتفاعلات

تُحفظ التفضيلات الصريحة في جداول علائقية بدل قوائم نصية. أما `user_interactions` فيحفظ الحدث الخام وتوقيته ويفصل بين تفاعل الطعام وتفاعل الوجبة. لا تُحوّل `CONSUMED` أو `MealLog` تلقائيًا إلى تقييمات، ولا تُفعّل CF من بيانات مصطنعة.

جدول `recommendations` يربط التفاعل بما عُرض فعليًا، ويدعم مصادر `CBF`, `CF`, `HYBRID`, و`RULE_BASED`. وجود البنية لا يعني أن CF جاهز للإنتاج؛ الجاهزية الفعلية تحتاج تفاعلات حقيقية، صريحة، وموافقًا عليها من عدد كافٍ من المستخدمين.

## 8. أثر البنية على ML

| المكوّن | الأثر |
|---|---|
| CBF | يحصل على مغذيات موحدة ووسوم وتصنيفات قابلة للاستعلام، مع استبعاد IDs كميزات عديمة المعنى. |
| التخصيص | يستطيع لاحقًا قراءة التفضيلات الصريحة دون تفسير سجل الوجبات تفسيرًا خاطئًا. |
| السلامة | تبقى الأدلة الغذائية والحساسية علائقية وقابلة للتدقيق قبل الترتيب. |
| K-Means | يستخدم المغذيات المعيارية للتنوع فقط، وليس لتشخيص المستخدم. |
| CF | توجد بنية لجمع الأحداث وربطها بالتوصيات، لكن التدريب غير مفعّل ولا توجد بيانات حقيقية كافية. |
| Hybrid | يمكنه الجمع بين القيود الصلبة ثم CBF ثم التنويع؛ لا يعيد score إدخال طعام غير مؤهل. |

## 9. الترحيل والتوافق

التغيير في `e7f1a2b3c4d5_add_normalized_food_meal_data_architecture.py` additive. ينشئ القواميس والجداول، يضيف `foods.category_id`، ثم يملأ التصنيفات وأنواع الوجبات والوسوم من السجلات الحالية. لا يحذف `users` أو `meal_logs` أو `weekly_plans` أو `user_food_feedback` ولا يغير عقد API الحالي.

يستخدم المستورد نفسه المزامنة عند استيراد كتالوج جديد. يجب تشغيل `alembic upgrade head` قبل الاستيراد في أي بيئة، وتبقى النسخة المرجعية في `data/catalog/food_catalog_reference.sqlite3` للكتالوج فقط وليست قاعدة تشغيل.

## 10. القيود المتبقية

لا توجد في هذه المرحلة بيانات وجبات مركبة جاهزة؛ جدول `meals` يبدأ فارغًا حتى تراجع وصفات موثوقة. كما لا توجد أدلة FoodAllergen مكتملة لجميع الأطعمة، ولذلك لا يمكن إعلان اكتمال سلامة الحساسية. بيانات التفاعل الحقيقية غير متوفرة، وCF يبقى بنية مستقبلية فقط. دعم الأطعمة الليبية التفصيلي والصور والميكرونutrients والتكلفة ووقت التحضير مؤجل عمدًا.
