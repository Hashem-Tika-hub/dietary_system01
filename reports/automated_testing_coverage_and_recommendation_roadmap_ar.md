## 2. ما الذي ينفذه خط الجودة الآلي

ملف `.github/workflows/quality.yml` يعرف مهمتين مستقلتين. الأولى تستخدم Python 3.12 وتثبت `requirements-dev.txt` ثم تنفذ `pytest -q api/tests`. الثانية تثبت Flutter stable، تنفذ `flutter pub get`، ثم `flutter analyze --no-fatal-infos` و`flutter test test`.

| الطبقة | الفحص الآلي الحالي | الحالة في آخر تشغيل لـ`main` | قياس التغطية المنشور |
|---|---|---|---|
| FastAPI وPython | `pytest -q api/tests` | ناجح | لا يوجد تقرير Coverage في CI بعد؛ القياس في هذا التقرير محلي وفعلي. |
| Flutter/Dart | تحليل ساكن + Unit/Widget Tests | ناجح | لا يوجد `lcov.info` أو نسبة رقمية في CI. |
| Integration Tests للهاتف | ملف الاختبار موجود | غير مدرج في خط CI الحالي | لا توجد نتيجة جهاز/محاكي ضمن هذا التقرير. |
| Database migrations | اختبارات ضمن API suite | ناجح | مغطى ضمن Python فقط. |

الاختبارات التكاملية الخاصة بتسجيل الوجبة وتحديث Dashboard موجودة في المستودع، لكنها ليست جزءًا من `flutter test test` لأنها تتطلب محاكيًا أو جهازًا وخادم FastAPI اختباريًا معزولًا. لذلك لا تُعد ناجحة تلقائيًا بمجرد نجاح اختبارات Widget.

## 3. منهجية القياس والمخرجات

تم تثبيت أداة `coverage` ثم تنفيذ الأمر التالي من جذر المستودع:

```bash
coverage erase
coverage run -m pytest -q api/tests
coverage json -o reports/api_coverage.json
coverage html -d reports/api_coverage_html
coverage report -m
```

أُنشئت المخرجات التالية داخل `reports/`:

| الملف أو المجلد | الغرض |

## 6. ما تحقق فعليًا في التوصية والحساسية

النظام يطبق الفلاتر الصارمة لنوع الوجبة والحساسية وعدم الرغبة والقيود المعرفة قبل ترتيب CBF أو CF. توجد رموز حساسية قياسية، وبدائل توافقية للقيم القديمة مثل الحليب والبيض والمكسرات والقمح والجلوتين. كما أن الاستبدال الأسبوعي المباشر أصبح يتحقق من مجموعة المرشحين المؤهلين نفسها، فلا يستطيع طلب API تجاوز الحساسية بطلب `fdc_id` يدوي.

قاعدة البيانات تحتوي طبقات قابلة للتدقيق للمكوّنات ومسببات الحساسية، ومنها حالات `present` و`absent` و`unknown` على مستوى المكوّن والطعام. لكن مسار التوصية الحالي يعتمد حقل `allergen_codes` في DataFrame المرشحين واحتياطي الفئات القديمة، ولا يستثمر بعد حالة الثقة الكاملة من جداول `FoodAllergen` و`IngredientAllergen` أثناء كل عملية توصية. هذه هي أهم فجوة وظيفية في الحساسية، وليست غياب الجداول.

> معلومات الحساسية الناقصة لا تثبت أن الصنف آمن. ينبغي أن تعرض الواجهة حالة البيانات الناقصة بوضوح، وأن توثق سياسة الاختيار بدقة بدل الادعاء بضمان طبي.

## 7. خارطة تطوير التوصيات الذكية وتصفية الحساسية

### المرحلة أ: تقوية مصدر الحقيقة للحساسية

ابدأ بإنشاء خدمة مستقلة مثل `allergen_eligibility.py` تبني قرار أهلية قابلًا للتدقيق لكل طعام من `FoodAllergen` و`IngredientAllergen` ومصدر المعلومة وتاريخ المراجعة. يجب أن يعود القرار بأحد الحالات: `eligible` أو `blocked` أو `unknown_metadata`، مع قائمة أسباب يمكن عرضها أو تسجيلها.

| العمل | النتيجة | اختبار القبول |
|---|---|---|
| توحيد الرموز والمرادفات | تحويل مدخلات المستخدم إلى قاموس رموز ثابت قابل للمراجعة. | اختبارات عربية/إنجليزية ومسافات وحروف كبيرة وتكرار. |
| تجميع دليل الحساسية | مزج حالة الطعام والمكونات ومصدر الكتالوج في قرار واحد. | صنف به مكوّن `present` يُحجب حتى إن كان الحقل السطحي ناقصًا. |
| سياسة البيانات المجهولة | إضافة وضع واضح للواجهة والسيرفر: تحذير أو استبعاد محافظ بحسب اختيار المنتج الموثق. | لا يُعرض الصنف المجهول على أنه «آمن». |
| تتبع القرار | تسجيل `allergy_filter_reasons` في استجابة بدائل الإدارة أو سجلات التقييم، لا في تفضيلات المستخدم. | إمكانية معرفة سبب استبعاد أو قبول كل صنف. |

### المرحلة ب: اختبار نهاية إلى نهاية للفلترة الصارمة

أنشئ Fixture كتالوج مصغرًا يحتوي على عناصر آمنة ومحظورة ومجهولة لكل حساسـية، ثم نفذ Smoke Tests عبر API الحقيقية لمسار الوجبة والبدائل والاستبدال والخطة الأسبوعية. يجب أن تثبت الاختبارات أن الحظر يحدث قبل CBF وCF وK-Means وأن `FoodRecommendation` لا يمكن أن يعيد عنصرًا محظورًا حتى لو كانت درجته أعلى.

تشمل الحالات المهمة: حساسية متعددة، رموز حساسية بصيغ كتالوج مختلفة، معلومات حساسية مفقودة، صنف متاح في أكثر من وجبة، بديل وحيد مؤهل، ومحاولة استبدال مباشرة بصنف محظور.

### المرحلة ج: رفع جودة التوصية بالمحتوى

بعد تثبيت الأمان، أضف اختبارات مكون حقيقية لـCBF باستخدام DataFrame صغير ثابت ونموذج محفوظ داخل fixture الاختبارات. الهدف ليس تدريب نموذج علاجي، بل التحقق من أن متجه الوجبة والحصة والسقف اليومي والتنوع تنتج ترتيبًا حتميًا ومتوافقًا مع القيود. يجب تغطية: هدف الوجبة الكامل، المتبقي اليومي، سقوف الحصص، خانات الطبق الإلزامية والمفقودة، وعدم التكرار الناعم للـClusters.

### المرحلة د: تقييم وظيفي قابل للعرض في مشروع التخرج

أضف مسار تقييم غير طبي يقيس مؤشرات هندسية: معدل الاستبعاد الصحيح للحساسية المعروفة، نسبة التوصيات ذات السبب، تنوع مجموعات K-Means، تغطية الكتالوج، وزمن الاستجابة. لا تسم هذه المؤشرات «فعالية صحية» أو «دقة طبية»؛ إنها قياسات سلامة واتساق وترتيب.

### المرحلة هـ: تحسين التفاعل وCF دون خلط البيانات

أضف سجل تعرض للتوصيات وموافقة صريحة منفصلة إذا رغبت لاحقًا في استخدام إشارات ضمنية. إلى أن تُنفذ الموافقة وسجل التعرض وتقييم زمني صحيح، يبقى CF معتمدًا فقط على `like` و`save` و`dislike` و`not_interested`. لا تستخدم `MealLog` لتفعيل CF أو توليد تقييمات اصطناعية.

## 9. التوصية التنفيذية التالية

أفضل خطوة برمجية تالية هي **المرحلة أ ثم المرحلة ب**: ربط مصدر حقيقة الحساسية الموجود في قاعدة البيانات بخدمة أهلية مستقلة، ثم اختبارها من طرف API حتى الاستبدال الأسبوعي. هذه الخطوة تعالج أكبر فجوة متبقية في سلامة بيانات الحساسية، وترفع جودة المشروع دون الحاجة إلى بيانات مستخدمين كثيرة أو ادعاءات طبية.

بعد ذلك يبدأ العمل على Fixtures لنموذج CBF والاختبارات الحقيقية للمحرك. عند اكتمال هاتين الخطوتين يصبح من المناسب إضافة Coverage إلى CI بوصفه جودة مستمرة، لا رقمًا ثابتًا في تقرير واحد.
